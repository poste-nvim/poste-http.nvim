1. INTRODUCTION                                          *poste-intro*

Poste HTTP is a keyboard-first HTTP request executor for Neovim.
Write requests in `.http` / `.rest` files and execute them inline
with `<CR>`.

==============================================================================
2. HTTP SYNTAX                                        *poste-http-syntax*

A `.http` file contains one or more request blocks separated by `###`
markers.

REQUEST BLOCK ~
                            *poste-http-block*
Every request block starts with a `###` line:

    ### My Request Name
    GET {{base_url}}/endpoint
    Content-Type: application/json

    {"key": "value"}

    ### Another Request
    POST {{base_url}}/submit
    Content-Type: application/json

    {"data": "hello"}

Request blocks are separated by `###` markers. The text after `###` is
the request name, shown in the history list.

METHOD LINE ~
                            *poste-http-method*
The first non-comment line after `###` is the request line:

    GET /api/items
    POST /api/items
    PUT /api/items/1
    PATCH /api/items/1
    DELETE /api/items/1
    HEAD /api/items

Beyond plain HTTP verbs, three methods have dedicated executors
(see |poste-http-multi-protocol|):

    GRAPHQL {{base_url}}/graphql    query body lowered to a JSON POST
    GRPC {{host}}/service/Method    via grpcurl (unary / server-streaming)
    WEBSOCKET {{base_url}}/ws       via websocat, frames in the Msgs tab
    SCRIPT                          body runs as an orchestration script

                                                    *poste-http-multi-protocol*
A `GRAPHQL` block's body is the query text; an optional trailing JSON
object is the variables block. `Content-Type: application/json` is
synthesized unless the block sets its own; pin an SDL schema for
body completion with `# @graphql-schema ./schema.graphql`.
`GRPC` resolves protos through server reflection or a pinned file
(`# @grpc-proto echo.proto`). `WEBSOCKET` opens an interactive session;
`<CR>` sends the block body as a frame. See docs/user/syntax.md for the
full reference.

HEADERS ~
                            *poste-http-headers*
Headers follow the method line, one per line:

    Content-Type: application/json
    Authorization: Bearer {{token}}
    X-Custom-Header: value

REQUEST BODY ~
                            *poste-http-body*
After headers, a blank line separates the body:

    POST /post
    Content-Type: application/json

    {"name": "test", "value": 42}

FILE BODY ~
                            *poste-http-body-file*
Use `< ./path` to read body from a file:

    PUT /upload
    Content-Type: image/png

    < ./image.png

COMMENTS ~
                            *poste-http-comments*
Lines starting with `#` are comments:

    # This is a comment
    GET /api

VARIABLE DEFINITIONS ~
                            *poste-http-variables*
Lines starting with `@` define block-scoped variables:

    @base_url = https://httpbin.org
    @token = my-secret-token

    GET {{base_url}}/get
    Authorization: Bearer {{token}}

==============================================================================
3. VARIABLES                                            *poste-variables*

Poste supports `{{variable}}` interpolation in request lines, headers,
and body.

VARIABLE SOURCES ~
                            *poste-http-var-sources*
Variables can come from:

  - Block scope: `@name = value` lines
  - Environment files: `env_name = value` in `.env.json`
  - Inline overrides: `(#name) @var=val` in block header
  - Pre-script output: variables returned by `> {% ... %}`

ENVIRONMENT FILES ~
                            *poste-http-env-file*
Create `.env.json` files:

    {
      "dev": {
        "base_url": "http://localhost:3000"
      },
      "prod": {
        "base_url": "https://api.example.com"
      }
    }

Switch environments with `:PosteHttpEnv [name]` or `<leader>vv`.

==============================================================================
4. PRE/POST SCRIPTS                                      *poste-scripts*

Pre-scripts run before the request is sent. Post-scripts run after
receiving the response.

PRE-SCRIPT SYNTAX ~
                            *poste-http-prescript*
    GET /api

    > {%
      request.variables.token = "computed-token"
      client.log("Token set")
    %}

The `request` object exposes `request.variables` to set variables
before execution.

POST-SCRIPT SYNTAX ~
                            *poste-http-postscript*
    GET /api

    < {%
      client.log("Status: " .. response.status)
    %}

The `response` object contains the full response data.

INLINE SCRIPTS ~
                            *poste-http-inline-script*
Short scripts can be written inline between `{%` and `%}`.

EXTERNAL SCRIPT FILES ~
                            *poste-http-external-script*
    GET /api

    < ./scripts/my_assertion.lua

EXTERNAL SCRIPT FILES ~
                            *poste-http-script-file*
Scripts in separate `.lua` files are imported with `< ./path.lua`.

SANDBOX ~
                            *poste-http-sandbox*
Scripts run in a sandboxed environment with limited globals:

    assert     error      ipairs     math
    next       pcall      pairs      string
    table      tonumber   tostring   type
    client     request    response   variables
    env        os         io         md5

==============================================================================
5. ASSERTIONS                                            *poste-assertions*

Assertions validate the response after execution using `client.assert`.

SYNTAX ~
                            *poste-http-assert*
    GET /api

    > {%
      client.assert(response.status == 200, "Expected 200")
    %}

ASSERTION HELPERS ~
                            *poste-http-assert-helpers*
  - `client.assert(condition, message)` - fails if condition is false
  - `client.log(message)` - adds to log output
  - `response` - response table with status, headers, body, etc.
  - `request` - the original request table

==============================================================================
6. RUN DIRECTIVE                                          *poste-run*

The `run` directive lets one request file import and execute requests
from another file.

SYNTAX ~
                            *poste-http-run*
    run #RequestName
    run #alias.RequestName
    run ./path/to/file.http

IMPORT STATEMENT ~
                            *poste-http-import*
To import a file with an alias:

    import ./auth.http as auth

Then reference it:

    run #auth.Login

VARIABLE OVERRIDES ~
                            *poste-http-run-vars*
Pass inline variables:

    run #auth.Login (@token=abc123)

==============================================================================
7. ENVIRONMENT                                            *poste-env*

Environments manage variable sets for different deployment targets.

ENVIRONMENT FILE ~
                            *poste-http-env*
Place a `.env.json` file alongside your `.http` file or in a parent
directory. See |poste-http-env-file| for format.

SWITCHING ~
                            *poste-http-env-switch*
Use `:PosteHttpEnv [name]` to switch, `<leader>vv` for the environment
picker. The current environment is shown in the winbar.

8. KEYMAPS                                              *poste-keymaps*

    <CR>                   Execute request at cursor
    <M-CR>                 Execute request (horizontal split)
    ]] / [[                Jump to next/previous request block
    gd                     Go to variable/request definition
    grr                    List variable references (quickfix)
    gs                     Toggle request outline (opens on the request at cursor)
    K                      Show variable value / response chain
    gi                     Open variable inspector
    <leader>rp             Paste curl command as request
    <leader>rc             Copy request as curl command
    <leader>vv             Pick environment
    <leader>l              Show request history
    ga                     Ask the AI about the request (poste-ai.nvim)
    g?                     Show keymap help window

Keymaps are set in `poste_http` buffers. See the help window (g?) for the
response/history keymaps; all of them are configurable via `setup()`.

10. BOUNDARY HIGHLIGHT                                  *poste-http-boundary*

:PosteHttpBoundary toggles the request-block boundary highlight: while on,
the block under the cursor is marked so you can see where it starts and
ends. Which style of marking is used is `boundary_style`
(|poste-http-boundary-style|). Both styles follow the cursor across every
`poste_http` buffer.

                                                    *poste-http-boundary-style*
`boundary_style` picks how the request block under the cursor is marked.
Both styles are switched on and off together by `:PosteHttpBoundary`.
    "background"  default. A full-width `PosteHttpBoundary` rectangle
                  behind every line of the request block (reaching the
                  window edge, wrapped lines included).
    "gutter"      no tinting of the text — only the number column of those
                  lines is shaded, so the parser's own colours stay
                  readable. `▏` below marks the shaded cell:
>
                      ▏ 1  ### Login
                      ▏ 2  POST {{base_url}}/login
                      ▏ 3  Authorization: Bearer x
<
                  Needs a number column ('number' or 'relativenumber'); with
                  neither, the style marks nothing. The shade is
                  `PosteHttpBoundaryGutter`, which links to
                  `PosteHttpBoundary` so one |nvim_set_hl()| moves both.

>lua
      require("poste-http").setup({
        boundary_style = "background", -- or "gutter"
      })
<

11. HIGHLIGHT GROUPS                              *poste-http-highlights*

Every group the plugin styles is named `Poste*` and gets a default style
on each colorscheme change.

                                                    *poste-http-hl-override*
Recolour groups through the `highlights` table in setup(): the override
applies immediately and is re-applied on every colorscheme switch, so it
survives switching themes:
>
      require("poste-http").setup({
        highlights = {
          PosteMethodGET = { fg = "#98c379", bold = true },
          PosteStatus4xx = { fg = "#e5c07b" },
        },
      })
<
`:highlight PosteLatency guifg=#ff0000` also works for the linked groups
below, but groups the plugin re-styles with fixed colours on every
setup (methods, status codes, boundary, response views) would be reset.

Source-buffer groups exist in three forms: the plain `PosteComment`
(used by the Vim syntax engine), `@PosteComment` and
`@PosteComment.poste_http` (used by the tree-sitter highlighter). A
`highlights` override is applied to all defined forms at once, so one
entry recolours the buffer under either engine.
